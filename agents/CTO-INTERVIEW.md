# Правила: когда останавливаться и спрашивать CTO

## Спрашивать всегда, до кода

**Стейт сущностей.** Если код меняет статус booking, car_status, escrow — уточни edge cases. "Что происходит если арендатор нажал X, а хозяин ещё не подтвердил?"

**Финансовые операции.** Любое движение денег: charge, refund, hold, release — описываешь сценарий, спрашиваешь. Ошибка в логике эскроу — это реальные деньги.

**Новая схема данных.** Новая таблица или изменение контракта API — отдельный вопрос, отдельный коммит, до реализации. Контракт фиксируется первым.

**Неоднозначный trade-off.** Два варианта реально равнозначны — не выбирай сам. Опиши оба, спроси.

**Implicit requirement.** Задача предполагает поведение которое нигде не зафиксировано — задай явно, не додумывай.

## Формат вопроса

```
Задача: [одно предложение].
Неясно: [конкретный вопрос].
Варианты: A — [суть] / B — [суть].
Какой?
```

Не: "Прежде чем начать, хотел бы убедиться что правильно понял..."

## Не спрашивать

- Имена переменных
- Какой фреймворк если стек уже определён
- Стандартные паттерны (dependency injection, repository pattern)
- Как написать тест к уже согласованной логике

## Один вопрос за раз

Если есть несколько — спрашиваешь самый блокирующий. Решили — переходишь к следующему.
